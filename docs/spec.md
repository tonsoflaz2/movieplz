# MoviePlz — product spec

> A Laravel + HAM hypeapp that lets a Plex server host receive media requests
> from friends and family, without giving anyone a login. Frictionless on the
> client side; a curated, human-in-the-loop pipeline on the host side.
>
> (Internally: a place to serve up the freshest hams.)

## 1. Why this exists

The host (initially: the project owner) runs a Plex server that friends and
family stream from. People frequently want new titles added, but they're shy
about texting a request every time. A shared Google Sheet works but isn't
notified, doesn't confirm fulfilment, and isn't browseable.

MoviePlz is the replacement: a mobile app where clients can search the
current library, submit a request, and get pinged when the host has added
it. Zero friction, zero accounts.

**Out of scope, by design:**
- Direct Plex API integration (the host does not want this — curation is manual and intentional).
- Automated downloads or any replacement of the host's sourcing workflow.
- A public social network. This is friends-and-family only.

## 2. Roles

| Role | Who | What they do |
|---|---|---|
| **Host** | One person. Initially the project owner; v2 may allow multiple. | Seeds the library, generates invites, receives incoming requests, marks them fulfilled when the title has actually been added to Plex. |
| **Client** | Anyone the host has shared an invite code with (family, friends). | Browses / searches the library, submits requests, sees their own request history and fulfilment notifications. |

## 3. Identity model — "no login"

Both the host and a likely majority of clients have a strong preference for
**not having traditional accounts**. No email, no password, no OAuth. The
model below gets us authenticated clients without any of that, using
**ephemeral 5-digit codes** that the host generates on demand and transfers
to the friend out-of-band (text, phone call, in person).

### 3.1 Concepts

- **Invite** — a short-lived 5-digit numeric code generated by the host on demand. Single-use, expires in 10 minutes by default. The host and client **speak separately** (outside the app) to transfer the code — phone call, text, in person, whatever. There is no persistent "permanent invite link" concept; each person gets a fresh code per onboarding.
- **Client** — a record created when an invite is redeemed. Stores a human-chosen `display_name` and is permanently tied to the mobile shell via a Laravel session cookie.
- **Session cookie** — the actual credential. The hypeapps mobile shell automatically persists every cookie the server sets, using the framework's built-in secure storage. Cookie lifetime is bumped to 5 years so clients never have to re-onboard unless the host explicitly revokes them. The client never handles a token; it just enters a code once.

### 3.2 Flow

```
Host onboarding (one-time, no env vars)
  │
  ▼
  $ php artisan host:mint-code
  > Host code: 73925  (expires in 10 min)
  │
  ▼ host opens app, types 73925, enters display name
  │
  ▼ server sees grants_host=true on invite, creates the hosts row
    and the host's clients row (role='host'), burns the invite
  │
  ▼
  host/home.ham (authenticated as host)

Client onboarding (host-driven)
  │
  ▼ host taps "Generate invite code" in their app
  │
  ▼ server creates invite, returns HAM showing the 5 digits + countdown
  │
  ▼ host speaks separately with friend, reads code aloud
  │
  ▼ friend opens app, types 73925 on invite screen
  │   POST /onboarding/invite  (rate-limited to 5/min/IP)
  │
  ▼ code valid + unredeemed + unexpired?
  │
  ▼ yes → name entry
  │
  ▼ POST /onboarding/name
  │
  ▼ server creates clients row, burns invite (redeemed_at = now()),
    stores client_id in session, Laravel sets session cookie
  │
  ▼
  home.ham (authenticated as client)

Subsequent launches
  │
  ▼ shell sends persisted session cookie automatically
  │
  ▼ session resolves to a clients row → home.ham
  │    session empty/revoked → back to onboarding
```

Host onboarding is NOT self-serve in the product sense (the host can't sign
up via a form). The `host:mint-code` artisan command is the only way to
claim host-ship, and it errors once a host already exists. v2 can add
self-serve host signup if anyone ever wants to run their own MoviePlz
instance on shared infrastructure.

### 3.3 Revocation

The host has a "connected clients" screen listing every client `display_name`.
Tapping revoke sets `clients.revoked_at`. On that client's next request, the
`RequireClient` middleware sees the revoked timestamp, clears the session,
and returns the invite-entry HAM. The shell picks up the new (empty) session
cookie automatically — no "clear your token" instruction needed from the
server side. From the user's perspective: they tap the app, see invite entry
instead of home.

### 3.4 Rate limiting

`POST /onboarding/invite` is throttled to **5 attempts per minute per IP**
to defend 5-digit codes against brute force. Combined with 10-minute expiry
and single-use semantics, the effective window for guessing is ≈50 attempts
against a ~100,000-combination space — safe.

## 4. Data model

All tables live under the default Laravel connection. Migrations go in
`database/migrations/`.

### 4.1 `hosts`
| Column | Type | Notes |
|---|---|---|
| `id` | bigint PK | |
| `name` | string | Display name shown to clients ("Christian's library"). |
| `created_at`, `updated_at` | | |

Seeded with one row in v1.

### 4.2 `library_items`
Mirror of the host's existing Google Sheet, searchable in-app.

| Column | Type | Notes |
|---|---|---|
| `id` | bigint PK | |
| `host_id` | FK → hosts | |
| `title` | string | As displayed ("The Matrix"). |
| `sort_title` | string | Articles moved to end ("Matrix, The") for alpha sorting. |
| `type` | enum `film`\|`series` | |
| `year` | smallint nullable | |
| `tmdb_id` | string nullable | Stretch; populated when metadata is enriched. |
| `poster_url` | string nullable | Stretch. |
| `added_at` | timestamp | When the host added this to Plex (not when the row was created). |
| `created_at`, `updated_at` | | |

Indexes: `host_id`, full-text on `(title, sort_title)` for search.

### 4.3 `invites`

Ephemeral, single-use, short-lived. The host generates these on demand from
within the app (or via `host:mint-code` artisan for the very first one).

| Column | Type | Notes |
|---|---|---|
| `id` | bigint PK | |
| `host_id` | FK → hosts, nullable | Nullable because the first-ever host-bootstrap invite is created *before* the `hosts` row exists. Set to the host's id on redemption of `grants_host=true`, or pre-set for in-app client invites. |
| `code` | string(5), unique | Plain 5-digit numeric, e.g. `73925`. Unique across all active rows. |
| `expires_at` | timestamp | Hard-set to `now() + 10 minutes` at creation. Filter by this in lookups. |
| `redeemed_at` | timestamp nullable | Set on successful redemption. Once non-null, the row is burned and cannot be redeemed again. |
| `redeemed_by_client_id` | FK → clients, nullable | The client that redeemed it. Audit trail. |
| `grants_host` | boolean, default false | Set only by the `host:mint-code` artisan command. Redemption creates the host's `clients` row with `role='host'`. |
| `created_at`, `updated_at` | | |

Indexes: unique `code`, `expires_at` for cleanup cron, `(host_id, created_at)` for the host to see their own history.

### 4.4 `clients`
| Column | Type | Notes |
|---|---|---|
| `id` | bigint PK | |
| `host_id` | FK → hosts | |
| `invite_id` | FK → invites nullable | Which invite they came in through. Nullable because the invite row may be cleaned up eventually. |
| `role` | enum `client`\|`host`, default `client` | The host is a row in this table too — same auth flow, different role. |
| `display_name` | string | Free text, not unique. |
| `device_token` | string, nullable | Random 40-char string generated at onboarding. **Audit-only** — not used for auth (Laravel sessions handle that). Useful for "this row was the one onboarded from that phone" if we ever add observability. |
| `revoked_at` | timestamp nullable | |
| `last_seen_at` | timestamp nullable | Touched by `RequireClient` middleware on every authed request. |
| `created_at`, `updated_at` | | |

Indexes: `(host_id, role)`, `revoked_at`.

### 4.5 `requests`
| Column | Type | Notes |
|---|---|---|
| `id` | bigint PK | |
| `host_id` | FK → hosts | |
| `client_id` | FK → clients | |
| `title` | string | What the client typed. |
| `year` | smallint nullable | |
| `type` | enum `film`\|`series` nullable | Not required — client may not know. |
| `notes` | text nullable | Free field ("season 2 specifically"). |
| `status` | enum `pending`\|`fulfilled`\|`declined` | Default `pending`. |
| `fulfilled_at` | timestamp nullable | |
| `fulfilled_library_item_id` | FK → library_items nullable | When host marks fulfilled, they can link to the actual row they added. |
| `seen_by_client_at` | timestamp nullable | When client first saw the fulfilled-state in their history — used to suppress repeat notifications. |
| `created_at`, `updated_at` | | |

Indexes: `(host_id, status)` for the host's incoming-request feed, `(client_id, created_at)` for the client's history view.

## 5. Screens (Blade views) and routes

All views live under `resources/views/ham/` as Blade templates
(`*.blade.php`). Despite the directory name, **these are fully dynamic
server-rendered Blade files** — loops, conditionals, Eloquent access, auth
helpers, request state, the lot. The *output* of that Blade rendering is
HAM markup, which the mobile shell parses on the other end; routes return
`text/html` so the shell treats the body as markup. Everywhere this spec
says "HAM template" it means "a Blade view that renders HAM". See
`CLAUDE.md` for the Blade-vs-HAM disambiguation rules.

### 5.1 Shared

| Route | View | Purpose |
|---|---|---|
| `GET /main.ham` | `ham/main.blade.php` | Entry point. Branches on `X-Client-Token` header: valid → redirect (or inline render) home; missing/invalid → onboarding. |

### 5.2 Onboarding

| Route | View | Purpose |
|---|---|---|
| `GET /onboarding/invite.ham` | `ham/onboarding/invite.blade.php` | Code entry form. |
| `POST /onboarding/invite` | returns partial | Validate code. On success: render name entry partial and swap `#main`. On failure: render inline error. |
| `POST /onboarding/name` | returns home partial + sets token | Create `clients` row, mint device token, instruct the shell to persist it, return the home HAM. |

The device-token-persistence step requires one piece of framework
cooperation: a HAM action the mobile shell understands as "store this value
under key X in secure storage". Check `docs/ham-reference.md` for the
current incantation — if there's no built-in tag, add this to the v1
blockers list (§8).

### 5.3 Client

| Route | View | Purpose |
|---|---|---|
| `GET /home.ham` | `ham/client/home.blade.php` | Search bar, "request new" button, recent requests strip, unread-fulfilled banner. |
| `GET /library.ham` | `ham/client/library.blade.php` | Paginated browse of host's library (poster grid if metadata present, else list). |
| `GET /library/search.ham?q=…` | `ham/client/_library_results.blade.php` | Swappable partial returned into `#library-results`. |
| `GET /requests/new.ham` | `ham/client/request_form.blade.php` | Form: title, year (optional), type (optional), notes. Prefills from query string if coming from library ("this isn't the one I want, but similar"). |
| `POST /requests` | returns partial | Creates `requests` row; returns a confirmation partial with a "request another" button. |
| `GET /requests.ham` | `ham/client/requests.blade.php` | Client's own request history, grouped by status. |

### 5.4 Host

Served under `/host/*` and gated by `RequireHost` middleware (the host is a
`clients` row with `role='host'`, resolved via the Laravel session).

| Route | View | Purpose |
|---|---|---|
| `GET /host/home.ham` | `ham/host/home.blade.php` | Pending requests count, preview of latest 5, library stats, "Generate invite code" button, unread badge polled every 30s. |
| `GET /host/requests.ham` | `ham/host/requests.blade.php` | Full incoming request list, filterable by status. |
| `POST /host/requests/{id}/fulfill` | returns row partial | Marks fulfilled, optionally links to a `library_items` row. |
| `POST /host/requests/{id}/decline` | returns row partial | Marks declined. |
| `POST /host/invite-code` | returns partial | Creates a fresh 5-digit invite with 10-minute expiry and returns a HAM partial showing the big code + countdown. No persistent admin list — if the host wants another one, they tap again. |
| `GET /host/clients.ham` | `ham/host/clients.blade.php` | List of connected clients (only `role='client'`), display_name / invited_via / last_seen / revoke button. |
| `POST /host/clients/{id}/revoke` | returns partial | Sets `revoked_at` on the target client. |

## 6. Library sync

v1 ingests the host's Google Sheet via an artisan command:

```
php artisan library:import path/to/export.csv
```

Expected CSV columns: `title`, `sort_title`, `type`, `year`. The command is
idempotent — re-running with an updated export upserts by `(host_id, title,
year)`.

**Stretch**: direct Google Sheets API sync on a schedule, or a host-side
"upload CSV" route. Not required for v1.

## 7. Notifications

Two directions of notification matter:

1. **Host → learns about incoming requests.**
2. **Client → learns when their request has been fulfilled.**

### v1: polling + in-app only

No push infrastructure. Both directions use in-app indicators:

- The host home screen polls `GET /host/home.ham` on a sensible interval (via a HAM `<timer>` / `<poll>` tag, whichever the framework supports — check the reference) and shows an unread badge on the requests tab.
- The client home screen does the same for fulfilled requests, showing a banner "X was added! Go watch it" until the client acknowledges.

### v2: push

Add APNs/FCM via the hypeapps shell. Host gets pushed on every new request;
client gets pushed when their request flips to `fulfilled`. Requires:

- Device push tokens stored on the `clients` / host row.
- A Laravel notification channel that talks to the hypeapps push relay.
- The mobile shell granting notification permission on first launch.

## 8. Stretch goals — catalogued, not committed

These came up in ideation but should not block v1. Each is listed with the
reason it's deferred.

| Feature | Why deferred |
|---|---|
| **Rich metadata (posters, descriptions, cast) from TMDB** | Requires a TMDB API key, a background job to enrich library rows, and a fuzzy-match layer. Nice, but v1 can ship with title + year + type alone. |
| **Duplicate detection on request submit** | Needs fuzzy title matching — the client will often type something slightly different from the canonical title. Hard to get right. Worst case in v1: the host sees a duplicate and declines with "already in library", which is fine. |
| **Multi-host support** | v1 has one host seeded in DB. Multi-host requires self-serve host signup (which re-introduces a login concept for hosts), host namespacing on invites, and a "which host?" step during client onboarding. Fine for v2. |
| **Push notifications** | See §7. Blocks on framework support and push relay setup. |
| **Browsing the host's library by category / genre / decade** | Requires richer metadata (see row 1). |
| **Client-to-client visibility ("who else asked for this?")** | Explicitly not wanted — clients should feel private. Leaving it off. |
| **Automated Plex download pipeline** | Explicitly not wanted by the host. The human curation step is the whole point. |

## 9. v1 blockers — RESOLVED

All four original blockers were investigated against the framework source
and the showcase app. Full writeups in `docs/plan.md` §1. Summary:

- [x] **Secure-storage device-token action** — *not needed*. The mobile shell already persists cookies via `flutter_secure_storage` automatically (`hypeapps/lib/src/controls/network_manager.dart:18-48`). Drop the `X-Client-Token` design; use standard Laravel session cookies with a 5-year lifetime. The spec has been updated to reflect this (see §3).
- [x] **HAM polling tag** — native. `trigger="every 30s"` on any element with an `action=` attribute (`hypeapps/lib/src/controls/hypermedia_controls.dart:1735`, example in `showcase_app/assets/html/showcase/demo_triggers.ham:127`). Auto-cancels when the element is swapped out.
- [x] **HAM form → partial swap with status codes** — the framework does not distinguish 422 from 500 (`network_manager.dart:617-639`). Resolution: HAM routes always return **HTTP 200**, even for validation errors, with inline error HAM. A custom exception renderer installed in `bootstrap/app.php` catches any unhandled error and returns `ham.partials.error` at status 200.
- [x] **Remote poster image loading** — native `<img src="https://...">` with built-in disk cache (`ham-reference.md:823-838`). Stretch §8 row 1 is cheap whenever we decide to enrich.

## 10. Implementation order (suggested)

1. **Config + exception renderer.** Session lifetime, cookie name, HAM-route 200-always exception handling.
2. **Migrations + models + support classes + seeders.** Includes `host:mint-code` and `library:import` artisan commands and a sample CSV fixture.
3. **Onboarding flow end-to-end.** Middleware, invite entry, name entry, view composer for `$current_client`. This is the hardest piece — do it first so everything after it is CRUD.
4. **Client home + library browse + search + request form + history.**
5. **Host home + incoming requests + fulfill / decline + generate-invite button.**
6. **Host client revocation.**
7. **In-app polling / unread badges** for both directions.
8. **Tests** — auth flow, import idempotency, request lifecycle, invite redemption rules.
9. Stretch goals, one at a time, only if v1 survives contact with real use.

See `docs/plan.md` for the executable, file-by-file version with smoke
tests at each phase boundary.

## 11. Naming

The product is **MoviePlz** (matches the repo, the Flutter shell bundle id,
and the fact that the whole thing started with "my wife keeps saying movie
please"). "Plex Request" is a fine description but not the brand.
